【この教材の目的】
プログラムの知識がないソロプレナーが、自分用の告知ツールを作り、以後も使う。

【実装要件】
1. 本人だけがアクセスできるSitesのWebアプリを作る。既存の本人用ツールを更新する場合は本人の対象指定を確認し、既存データを保護する。講師のサイトID・認証・DBは使わない。
2. 画面は「告知を作る」「事業情報」「設定」。制作順がわかる、読みやすく落ち着いた仕事場にする。スマートフォンでも操作可能にする。
3. 告知入力は「何を告知したいか」「詳しい情報」「文体・必ず伝えたいこと」の3欄。最初だけ必須。未定の情報を入力必須にしない。直接入力とテキストの貼り付けを用意。
4. 事業名・事業内容・呼び名・強み・料金と提供形式・活動範囲・リンク・希望文体・避けたい表現を共通情報として保存。未入力でも制作できる。今回の条件と共通情報を混同しない。
5. 作成対象はキャッチコピー3案、チラシ掲載文、LPの構成・文章、X投稿、Instagram投稿、LINE配信、案内メール、確認リストの8種類。選択生成と一括生成を用意。
6. AIをサイト内部で直接呼び出さない。「依頼文をコピー」してWorkに送る。生成依頼には今回の材料、必要な事業情報、対象媒体、コピーとレビューの基準を含め、LPの場合はデザイン基準も入れる。後続の別Workにも必要な指示が届くこと。
7. 返答はrequestIdとresults[{id,text,warnings}]のJSON。本人が貼り付け、プレビューし、確認して保存。本文だけの貼り付けは説明つきで拒否。別依頼ID・重複・未依頼・取り込み済み媒体を拒否。部分取り込みは可能。
8. 個別の書き直し・短縮・やわらかく・強く伝える依頼を作れる。事実と未定を変えない。入力が変わった結果は古いと表示し、最新として扱わない。
9. LP結果が保存できたら「LP制作の依頼文をコピー」。入力事実・LP本文・未解決事項・3つの制作基準を含める。新しいWorkへ送ればLPを制作できる指示にする。入力変更後は古いLPからこの指示を作れないようにする。
10. 入力・事業情報・設定・返答・依頼状態を本人用DBに保存。再読み込みで復元。保存失敗を成功と表示しない。他の端末との上書き競合を検知する。APIにも本人認証をかける。
11. 配色・表示名とライト／ダークの設定を用意。テスト情報の印は出力・コピー・LP依頼へ引き継ぐ。「新しい告知」は消える対象を説明して確認し、事業情報は残す。
12. サーバー認証、入力検証、秘密保護を守る。利用できない機能をできたと装わない。Sitesが使えない場合は不足を短く説明し、できたファイルを残す。別の製品を受講生に導入させて回避しない。

# 寺子屋AI コピーライティング

読み手が「自分向けか」「何が得られるか」「次に何をすればよいか」を無理なく理解できる文章を作る。派手な言い回しより、事業主本人の言葉、具体性、読みやすさを優先する。

## 最初に整理すること

入力から次の5点を整理する。既に分かっている内容は質問し直さない。

1. 告知対象：商品、サービス、イベント、セミナーなど
2. 読み手：誰が、どんな状況で読むか
3. 約束：読み手が得られる具体的な変化または持ち帰り物を1つ
4. 根拠：提供内容、進め方、実績など入力済みの事実
5. 次の行動：申込み、問い合わせ、詳細確認など

文章作成に不可欠な事実が足りない場合だけ、不足分を簡潔に確認する。日時、料金、会場、定員、申込先などが未定でも制作できる場合は、未定のまま扱って先へ進む。

## 事実と安全

- 入力にない価格、日時、住所、URL、連絡先、定員、資格、実績、割引、残席、保証、口コミ、体験談、比較優位を作らない。
- 「未定」は未定のまま示す。申込先が未定なら「受付準備中」など、現状が分かる表現を使う。
- 効果や成果を断定しない。「必ず」「絶対」「誰でも」「これだけで」など根拠のない保証を避ける。
- 不安をあおり、急がせることだけを目的にした表現を使わない。
- デモ、テスト、架空情報の指定がある場合、すべての対象出力にその表示を残す。
- 事業情報は背景、今回の入力は今回の条件として扱い、今回限りの条件で事業プロフィールを書き換えない。
- 矛盾を判断できないときは、勝手に片方を採用せず注意点として示す。

## 日本語の基準

- 事業主本人がお客様へ話す声で書く。外部の広告会社が褒めているような文調にしない。
- 冒頭は具体的な状況、対象、持ち帰り物、日時などから始める。抽象的な時代論から始めない。
- 一文には主な意味を1つ置き、長い修飾や同じ語尾の連続を減らす。
- 読み手が普段使わない専門語や横文字は、平易な言葉へ置き換えるか短く説明する。
- 「本質」「価値提供」「課題解決」「これからの時代」など、内容を伴わない決まり文句を避ける。
- 読み手を責めず、できていないことへの羞恥や恐怖を利用しない。
- キャッチコピーは格好よさだけで決めず、「誰向け・何を得られるか」を優先する。
- CTAは押すと何が起きるかを具体的に書く。

## 作成手順

1. 入力事実と未定事項を分ける。
2. 一番伝えたいことを1文にする。入力にない主張を加えない。
3. 読み手の状況から、伝える順番を決める。
4. 指定媒体に合わせて初稿を作る。
5. 事実、自然な日本語、媒体適合、CTAの順に見直す。
6. 問題があれば直してから返す。解決できない注意点だけを明示する。

媒体別に作るときは [references/channel-guides.md](references/channel-guides.md) を読む。

## 出力

ユーザーが形式を指定した場合はそれに従う。指定がなければ、完成文を先に示し、未定事項や確認が必要な点だけを短く続ける。制作過程の長い説明は付けない。

# 媒体別ガイド

現在の依頼に必要な媒体だけを使う。文字数などをユーザーが指定した場合は、その指定を優先する。

## 汎用告知文

- 「何を・誰に・いつ・どこで・いくら・どう申し込むか」を、入力された範囲で含める。
- チラシ、Web、口頭案内へ転用できる素直な文章にする。

## 告知LP

基本順は、ファーストビュー、対象者、得られること、内容・進め方、提供者、実施概要、CTA、FAQ。

- ファーストビューの約束は1つに絞る。
- 対象者の悩みは責める表現にしない。
- 得られることは、抽象的な成長ではなく行動や持ち帰り物で示す。
- 実施概要は入力文字列を正確に扱う。
- CTAは序盤と末尾に置ける文章量にする。
- FAQの回答に、入力されていない条件を追加しない。

## チラシ

- 大見出し、短いサブ見出し、日時・場所・料金・申込方法、短いCTAの順にする。
- 画像に載せる情報は絞る。詳しい説明は本文やLPへ逃がす。

## メール

- 件名だけで何の案内か分かるようにする。
- 本文冒頭で結論を伝える。
- 申込方法を見つけやすくする。
- 署名は入力された事業名や名前だけを使う。

## X

- 冒頭1行で対象または持ち帰り物を示す。
- 日時と申込先が入力済みなら含める。
- ハッシュタグを増やしすぎない。

## Instagram

- 冒頭で投稿の主題を明らかにし、短い段落と改行で読む負担を下げる。
- ハッシュタグは告知対象と実際に関係するものだけにする。
- 絵文字は希望文体に合わせ、指定がなければ控えめにする。

## LINE

- 要点、日時、申込方法の順にする。
- 近しい相手へ送れる自然な文体にし、強い売り込み口調を避ける。

## JSONなどの構造化出力

- 指定されたキー、ID、依頼IDを変更しない。
- 指定された媒体だけを含める。
- 本文中の改行や引用符がJSONを壊さないようにする。
- 注意点がない場合も、指定された空配列などの形式を守る。

# 寺子屋AI Webデザイン

事業内容と利用者の目的からデザインを決める。流行の装飾を先に選ばず、「何のサイトで、誰が、何をするか」を見た目と情報構造へ反映する。

## 制作前の最小ブリーフ

次を把握する。分かっている内容を質問し直さない。

- サイトまたはツールの目的
- 主な利用者
- 最優先の行動
- 事業や商品の特徴
- 必須情報と未定情報
- 既存のロゴ、色、写真、サイト、参考デザイン

目的と主な利用者のどちらかが不明で、デザイン判断が大きく変わる場合だけ確認する。それ以外は妥当な仮定を明示して進める。

## デザイン方針を先に決める

実装前に短いデザイン方針を作る。

1. コンセプト：事業固有のモチーフや質感を1つ選ぶ。
2. 配色：背景、文字、主色、補助色、状態色を役割付きで決める。
3. 書体：本文と見出しの役割を決め、日本語表示を確認する。
4. レイアウト：読み順と主要CTAの位置を決める。
5. 記憶点：この事業らしさを担う要素を1つに絞る。

方針が別の事業にもそのまま使える一般論なら、事業内容に戻って具体化する。

## 画一的なAIデザインを避ける

- 内容をすべて同じ角丸カードへ分割しない。カードは独立した情報単位にだけ使う。
- グラデーション、発光、粒子、ガラス表現を「AIらしさ」の記号として自動的に使わない。
- 見出しの一語だけ色や斜体を変える処理を常套手段にしない。
- 意味のない英語ラベル、連番、罫線、矢印を装飾目的で追加しない。
- すべてのセクションへ同じ登場アニメーションを付けない。
- 装飾は、事業理解、読み順、操作の分かりやすさのいずれにも寄与しないなら削る。

## 情報設計とモバイル

- モバイル幅を最初から想定し、重要情報と主要操作を縦の読み順で成立させる。
- 本文を小さくして情報量を収めない。分ける、短くする、優先順位を下げる。
- CTAの文言は押した後の結果を表す。
- 未定の申込先に、動かないボタンを置かない。「受付準備中」など状態を明示する。
- 日時、料金、申込先など更新される情報を画像だけに閉じ込めない。
- フォーカス表示、十分なコントラスト、キーボード操作、動きを減らす設定を尊重する。
- 空状態、エラー、保存完了は、次にできる行動が分かる文言にする。

## ChatGPT WorkとSites

ChatGPT WorkまたはSitesで制作する場合は [references/work-sites-guidance.md](references/work-sites-guidance.md) を読む。

## 制作と確認

1. デザイン方針を決める。
2. コンテンツの読み順と主要導線を設計する。
3. 実装または制作する。
4. 実際の表示をPCとモバイル幅で確認する。
5. 文字切れ、余白、折返し、コントラスト、操作、未定表示を直す。
6. 見た目を良くするために事実を変更していないか最終確認する。

表示確認ができない場合は、確認済みと表現せず、未検証部分を明示する。

## 出力

ユーザーがサイト制作を求めた場合は、デザイン案の説明だけで終わらせず、利用可能な制作手段で実物を作る。デザイン相談だけの場合は、実装を勝手に開始しない。

# ChatGPT Work・Sites制作ガイド

## 役割

- このスキルは、デザイン判断と完成品質を担当する。
- Sitesが利用できる環境では、サイトの作成、保存、表示確認にSitesを使う。
- 外部公開、投稿、広告配信、メール送信は、ユーザーが明示的に求めた場合だけ行う。

## 制作時

- 既存サイトを直す場合、現在の画面、文章、導線、保存仕様を確認してから変更する。
- 本人専用サイトと顧客向け公開ページを混同しない。
- 本人専用情報を公開ページへ移さない。
- 入力、保存、再読込があるツールでは、見た目だけでなく状態保持を確認する。
- 既存機能をデザイン変更のために削除しない。

## LP

- ファーストビューは主要な約束と主要CTAを中心にする。
- 開催概要や料金はテキストとして確認できるようにする。
- CTAは申込先が存在するときだけリンクさせる。
- FAQは入力情報の範囲で答え、未確定条件を補完しない。

## 本人専用ツール

- 最初に「何を入力し、何が作られ、どこへ保存されるか」を理解できる画面にする。
- 長い説明を常時表示せず、例や補足は必要な場所に置く。
- 保存、コピー、取り込み、作り直しなど、結果が異なる操作を同じ文言にしない。
- 成功、未保存、エラー、未入力を色だけで区別しない。

## 確認

# 寺子屋AI クリエイティブレビュー

感想ではなく、公開または利用を妨げる問題を見つけ、直せる形にする。文章、デザイン、操作、事実の4面を一緒に確認する。

## 必要な材料

可能な範囲で次を使う。

- 元の事業情報や告知素材
- 完成した文章、画像、サイト、ツール
- 実際の表示またはスクリーンショット
- 目的と対象者
- 申込、保存、コピーなど主要操作の期待結果

材料がない項目は推測で合格にせず「未検証」とする。サイトや画像の見た目を評価するときは、コードや説明だけで判断せず、実際の表示を確認する。

## 優先順位

- P0：利用不能、重大な誤情報、公開範囲の事故、主要操作が完了しない
- P1：申込みや理解を大きく妨げる、事実の創作、重大な表示崩れ
- P2：分かりにくさ、モバイル問題、デザイン不統一、修正可能な品質低下
- P3：公開を妨げない仕上げや好みの改善

## レビュー手順

1. 元情報と完成物を照合し、日時、料金、URL、名前、未定事項、デモ表記を確認する。
2. 初見の読み手として、対象、内容、得られること、次の行動を確認する。
3. 表示できる成果物は、PCとモバイル相当で実際に確認する。
4. 主要操作を試せる場合、申込、保存、コピー、取り込み、リンクを確認する。
5. [references/review-rubric.md](references/review-rubric.md) で各面を点検する。
6. P0、P1、P2の順に修正する。
7. 修正後の表示と操作を再確認する。修正後を見ていない問題を解決済みにしない。

## レビューの書き方

各指摘には次を含める。

- 優先度
- 場所
- 現在どうなっているか
- なぜ問題か
- 具体的な修正
- 確認結果または未検証事項

曖昧な「もっと魅力的に」「高級感を出す」だけで終わらせない。文章なら差し替え案、デザインなら要素・位置・余白・文字・色・状態など、実行可能な修正を示す。

## 修正まで依頼された場合

- レビューだけで止めず、権限と制作手段の範囲でP0から修正する。
- ユーザーが残すと指定した表現、デザイン、機能を勝手に変更しない。
- 大きな作り直しより、問題に対応する最小の変更を優先する。
- 修正で別の問題を増やしていないか再確認する。

## 完了条件

- 合格：対応可能なP0、P1、P2が残っておらず、事実、主要表示、主要操作を確認できた。
- 条件付き：P3だけが残る、または利用に影響しない未検証項目がある。
- 要修正：P0、P1、P2が残る。

採点は比較には使えるが、重大な誤情報や操作不能を平均点で相殺しない。

# クリエイティブレビュー基準

## 1. 事実と安全

- 入力にない日時、料金、URL、実績、口コミ、資格、保証が加わっていないか。
- 未定の項目が確定したように見えないか。
- デモや架空情報の表示が残っているか。
- 本人専用情報が公開ページに出ていないか。
- 使用許可のない画像、ロゴ、文章が含まれていないか。

重大な不一致は点数にかかわらずP1以上とする。公開範囲の事故はP0とする。

## 2. コピー

- 誰向けか、何を提供するか、何が得られるかが分かるか。
- 事業主本人の自然な日本語になっているか。
- 抽象語、過剰な煽り、同じ語尾、長すぎる文が理解を妨げていないか。
- 媒体に合う長さ、改行、情報順になっているか。
- CTAは次に起きることが分かるか。

## 3. デザイン

- 事業内容に由来する明確な方針があるか。
- 情報の優先順位が文字サイズ、余白、位置で伝わるか。
- 同じ角丸カードや装飾の反復だけで構成されていないか。
- 色、書体、写真、アイコンの役割が一貫しているか。
- 装飾が本文や操作を邪魔していないか。

## 4. モバイルとアクセシビリティ

- 390px相当で横にはみ出さず、文字と操作が読めるか。
- 重要情報が小さすぎたり画像だけになったりしていないか。
- 文字と背景のコントラストが十分か。
- キーボードフォーカスと主要操作の状態が分かるか。
- 動きが多すぎず、動きを減らす設定に配慮しているか。

## 5. 導線と機能

- 最優先の行動が見つけやすいか。
- ボタンの文言と押した後の結果が一致するか。
- 動かないボタンや、画像内の偽ボタンがないか。
- リンク、保存、コピー、取り込み、再読込が期待どおり動くか。
- エラー時に入力が消えず、次の行動が分かるか。

## 6. 仕上げ

- 誤字、文字切れ、画像のにじみ、余白の不統一がないか。
- PCとモバイルで主要情報の順番が保たれているか。
- 公開前に残る注意点が利用者へ明示されているか。

## 参考採点

必要な場合だけ100点で比較する。

- 事実と安全：25
- 伝わりやすさとコピー：20
- デザインの一貫性：20
- モバイルとアクセシビリティ：15
- 導線と機能：15
- 仕上げ：5

P0またはP1がある場合は、合計点が高くても合格にしない。

# 告知一式AI Ver.3 — 運営・再現手順

## 今回の変更

    if(answer) fields[current]+="\n"+line;
  }
  if(recognized) return {fields:fields.map(s=>s.trim()),test:isTest(text),structured:true};
  if(kind==="profile"){
    const p=Array(9).fill("");let index=-1;
    for(const line of text.split("\n")){
      const clean=line.replace(/^#+\s*/,"").replace(/^[【\[]|[】\]]$/g,"").replace(/[:：]\s*$/,"").trim();
      const found=profileLabels.indexOf(clean);
      if(found>=0){index=found;continue;}
      if(index>=0) p[index]+=(p[index]?"\n":"")+line;
    }
    if(p.some(Boolean)) return {fields:p.map(s=>s.trim()),test:isTest(text),structured:true};
  }
  return {fields:[text,"",""],test:isTest(text),structured:false};
}

export function contrastColor(hex:string){

export function parseResponse(raw:string,job:Handoff|null):HandoffResponse{
 if(!job||!job.remaining.length)throw Error("先に作成するものを選び、依頼文を準備してください。");
 if(raw.length>500000)throw Error("結果が長すぎます。500,000文字以内で貼り付けてください。");
 let clean=raw.trim();const fence=clean.match(/^```(?:json)?\s*\n?([\s\S]*?)\n?```$/i);if(fence)clean=fence[1];
 let response:HandoffResponse;try{response=responseSchema.parse(JSON.parse(clean));}catch{throw Error("結果の形式を読み取れません。ChatGPTのJSONコードブロック全体をコピーしてください。");}
 if(response.requestId!==job.id)throw Error("別の依頼の結果です。現在の依頼文で作成した結果を貼り付けてください。");
 const ids=response.results.map(r=>r.id);
 if(new Set(ids).size!==ids.length)throw Error("同じ媒体が重複しています。ChatGPTに形式の修正を依頼してください。");
 if(ids.some(id=>!job.remaining.includes(id)))throw Error("依頼していない媒体、または取り込み済みの媒体が含まれています。");

}
